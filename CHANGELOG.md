- 2026-09-10 — `segment.ATOMS_VERSION` 4: the previous audit's extension widening was too wide. Adding the C/C++, build and binary families put `c`, `h`, `a`, `o`, `cc`, `so` and `mk` on the bare-filename allowlist, and those are not rare extensions that happen to resemble attribute access — they are its spelling. `self.c`, `obj.h`, `df.a`, `x.o` and `node.so` were all registering as filenames, and `env` was the same shape from the other side (43 of its 47 corpus mentions are `process.env`, `self.env` or `interp.env`). Two structural rules replace v3's claim that every entry had been confirmed file-like. The seven ambiguous extensions come off the bare-filename list and are recognised **only inside a path**, since the slash and drive patterns never consult that list — `src/main.c` and a drive-qualified Windows path still extract. The criterion is the collision, not the length: `py`, `js`, `ts`, `md` and `sh` name files far more often than they name attributes and are untouched. And a dotted chain is no longer read as a filename: a match followed by a dot plus an identifier character is rejected, which is what `process.env.NODE_ENV` and `java.sql.Types` are, with a second extension exempted and consumed instead, so `node.tar.gz` and `device.svelte.ts` come out whole where the unfixed pattern yielded the truncated `node.tar` and outright rejection would have yielded nothing at all. `kts` is the one entry that is new rather than restored, and it is there to make `build.gradle.kts` whole. Measured on the public transcripts, bare-filename matches fall 8,206 to 5,523; of the 2,683 lost, 2,585 are the seven extensions, 47 are `env`, and about 50 are chain rejections. The accepted cost, weighed rather than discovered: a bare `main.c` in prose is no longer an atom, and it still is inside a path. Rejected: dropping the seven extensions entirely, which loses the path case too, and the path case is the one where the string actually names a file. Also rejected: keeping them and relying on the chain rule alone, which fixes `process.env.NODE_ENV` and does nothing for a bare `self.c`. It landed in two passes — the path requirement first scoped by extension length, then narrowed to the seven by collision, with double extensions exempted afterwards — but nothing was swept between them, so the whole rule set ships under one stamp. `google_creds.json.enc` stays rejected as a known cost: nothing distinguishes it from a chain without readmitting chains.
- 2026-09-10 — `paths.PATHS_VERSION` 2: substitution used a blind `str.replace` per table row, which mangled any path that merely **contained** a tabulated one — with `main.c` in the table, `main.cpp` was emitted as `[P0]pp`. Sorting longest-first only ever protected paths that were both in the table. Nothing failed loudly, because `expand` still restored such text and the artefact stayed recoverable; what was wrong was the scored text and the atoms re-extracted from it, which had lost a file the table never promised to carry. Substitution now runs over the module's own path spans and replaces only where a whole span equals a table row, which also drops the cost from O(rows × text) to O(text), independent of table size — that matters because this now runs over every segment of the corpus rather than only over table building. The module also imports `segment._FILE_EXTENSIONS` instead of restating the pattern, which is the only arrangement in which the table and the recall metric cannot drift apart.
- 2026-09-10 — `code.TRANSFORMS_VERSION` 2, covering three output changes under one stamp on purpose: no grid has run since the stamp was introduced, so there are no records at version 1 for a finer-grained bump to invalidate, and the version log in the module says so. **`shrink_prose` slices the original text by offset** instead of rebuilding a prefix from `split_prose`'s output. `split_prose` normalises what it returns — strips each chunk, rejoins sentences with a single space, drops punctuation-only paragraphs — so the rejoined prefix was not a substring of its input, which quietly broke the one property this whole project promises about retained text. Only whitespace ever differed, so the chunks are re-located in the original by a whitespace-tolerant left-to-right walk and the original is sliced; a chunk repeated verbatim later cannot be matched against the wrong copy. **`quantize_tool_use` never returns empty and never returns something larger than its input.** Both were reachable: every key can be dropped or empty and an empty payload renders to nothing, and a payload of nested containers pays back more JSON scaffolding in `render_call` than `_shrink_arg` saved on its string leaves. An empty segment is the worse of the two, since it still reaches `embed_texts` in the coverage metric and contributes a degenerate vector to it. The guard is now "reject unless strictly smaller", which is the rule the rest of the module already used. **`render_call` no longer emits the tool name.** It reaches the renderer from the transcript record's metadata rather than from the segment's text, so it is neither a verbatim span nor a mechanically-defined pointer — the only two things this output is allowed to contain, per the pointer decision of the same day. It is also strictly bad on the metric rather than a trade: `MultiEdit`, `TodoWrite` and `NotebookEdit` all match the identifier pattern and so enter the rendered segment's atoms, while recall intersects against the atoms of the original text, which never held them; the tokens cannot buy recall back and they count against the ratio. Rejected: redefining it as a mechanically-defined pointer, which fails because a pointer's definition has to ship in the same output and there is nothing here to point at. Also rejected: keeping it silently, on readability. Removing it is what let the size guard tighten from "not larger" to "strictly smaller" — the name had been costing a short single-argument call almost exactly what dropping the JSON scaffolding saved.
- 2026-09-10 — Experiment D survives its own 600-job run. **A failing job no longer takes the run with it**: the exception is caught per job and recorded with its traceback in a `failures` list beside the records, and the run continues. A failure is deliberately not stored as a record — a record full of zeroes would be averaged into its method's curve, and a bad average is worse than a hole, because a hole can be counted and an average cannot be spotted. **Checkpoints flush every 10 jobs and are written atomically**, to a sibling temp file then `os.replace`: a direct write of ~500 KB is not atomic, and a kill mid-write left truncated JSON that the loader could only treat as unreadable, silently discarding and re-running a whole transcript's work. Ten jobs caps what a kill destroys at about 20 seconds of work, for under half a percent of run time. **A loud incomplete-run block now opens every summary**, counting both failures raised this run and planned cells absent from the checkpoints for any reason at all — an aborted earlier run, a `--limit`, a stamp bump. Every table below it interpolates over whatever cells exist, so a silent hole reads as a perfectly normal curve measured on fewer points, which is precisely the class of defect this project keeps finding in its own numbers. **The path-arm table's caption stated the opposite of the truth and is fixed**: the table cost is charged into the reported compression ratio ONLY, is NOT deducted from the selection budget, and arm results are therefore NOT budget-neutral — every cell reads as "at the same achieved compression", never as "at the same budget". **New `BAND_QUALITY_VERSION`** covers the runner's own quality-to-depth mapping, since `_band` hands `quantize_segment` the sweep's keep ratio as its fidelity knob. It lives in the runner rather than in `code.py` precisely because that mapping is the runner's decision: changing it would move neither `segments_digest` nor `TRANSFORMS_VERSION`, so stored band records would have kept loading as valid while describing a depth policy that no longer existed. Scoped to the banding methods, on the same terms as the other two stamps.

- 2026-09-10 — `exp_e_analysis`'s cross-checkpoint guard was dead and now fires. It keyed on a run-level `config` field that `SCHEMA_VERSION` 3 had removed, so it compared `None` with `None` on every checkpoint and could never trigger — a guard against averaging incompatible checkpoints together that had silently stopped guarding at the moment the schema changed. The method set is deliberately left out of the fingerprint: a method that failed on every ratio leaves the grid intact and shows up as a missing curve, whereas a changed ratio grid shifts every interpolation without saying so.
